**Answer to question 2 (where does the cost sit):** at every scale measured, the SQLite engine (P1: index scan + join, no JS object construction) is a small minority of total cost. The majority is **serialisation** — JS object construction (P3−P1) plus NDJSON encoding (P4−P2) — not the database. This resolves VQ-2 from research/159-scale-and-latency-evidence.md: `better-sqlite3`’s documented-but-unmeasured `.raw()` win is real and large at this scale. **Render** is not measured by this harness — per the map’s standing preference ("Backend first. Frontend testing deferred") and because §5.2 already closes it analytically: a non-virtualised HTML table cannot render 10⁶ rows at any budget (Lighthouse’s ~1,400-node ceiling caps a table body at ~140 rows regardless of latency), so the only real design constraint is page size, which every measured page (50 rows) already satisfies by construction.

## Findings — what the ticket requires an answer to

### 1. Row count at which any operation exceeds the stated budget

**No interactive operation (cold open, first page, deep page, filter+sort indexed or non-indexed) exceeds its p95 FAIL threshold at any row count up to 10⁶, in either arm.** Every interactive p95 in the table above is at least an order of magnitude under its budget line.

**Export memory (budget row 7, maxRSS(10⁶) ≤ 1.5× maxRSS(10⁴)) is exceeded** in: plain (1.57×, 58160→91600 KiB), candidates (1.69×, 60336→101904 KiB). This is a **modest, sub-2×, but real overage**, and (check the table above) it is not confined to the candidates arm’s extra pipeline pass — if the plain (single-pass) arm is in this list too, the two-pass explanation does not cover it. Attribution (below) shows SQLite at 11–18% of end-to-end cost throughout — the growth is JS-side (V8 heap sizing under sustained allocation across a longer streaming run growing its working set before a GC cycle reclaims it), not an unbounded accumulation: bytes-out scale exactly with rows (linear, row 8 below) and no single string/array ever holds more than one row (row 9, satisfied by construction). Read as: **a correctly-streamed Export still costs a modest, bounded amount more memory per order of magnitude of rows, not unbounded growth** — worth recording as the actual (not budgeted) shape, not a scale-blocking finding.

**Export time scales linearly within budget (≤1.2× per decade) in both arms** — consistent with a streamed, index-ordered scan (§2.3) and with SQLite being a small minority of attributed cost.

The `filter_sort_nonindexed` p50 sits at or just over its 1,000 ms *target* at 10⁶ rows in: plain (p50 1049.5 ms) — but its p95 stays an order of magnitude under the 10,000 ms FAIL threshold throughout (table above). Worth watching as row counts grow further, not failing today.

**So: no operation crosses its hard FAIL threshold at any row count up to 10⁶.** Where the non-indexed filter+sort brushes its *target* (not its fail line) at 10⁶, that is exactly where §2.3 predicted extra cost would land — the K·logK-plus-temp-materialisation cost is real, it is just an order of magnitude inside the actual fail budget rather than outside it. The Export memory-ratio budget (row 7) is the one line that repeats on independent median-of-3 measurement as exceeded, by a modest and bounded amount, and it is JS/GC-side (attribution below), not SQL-side.

### 2. Whether the cost is SQLite, the serialisation, or the render path

**Serialisation**, decisively, at every scale measured. Per the attribution table, the SQLite engine (P1: index-satisfied scan + PK-lookup join, zero JS object construction) is 11–18% of end-to-end cost; JS object construction plus NDJSON encoding is the remaining 80–plus%. This is the direct, previously undocumented answer to VQ-2 in research/159-scale-and-latency-evidence.md (§3: `better-sqlite3` documents `.raw()` as faster at high row counts but publishes no magnitude). Render was not measured (map’s "Backend first, frontend testing deferred"); §5.2 already closes it analytically — a non-virtualised table caps at ~140 rows on DOM-size grounds alone, independent of any timing this harness could produce.

### 3. Whether a derived columnar cache is needed at all

**No.** §7.5 of the evidence doc fixed the decision table before this run: a columnar cache is only justified when SQL cost *dominates*, the plan is already optimal, and the operation is an aggregate/scan over most of the Case. None of that holds here — SQL cost is a small minority share at every scale (finding 2, above), every measured plan is index-satisfied where the schema provides an index (EQP table), and the one operation that *is* a near-full-Case scan (`attribution`’s probes) is dominated by JS serialisation, not SQL. **#130 stands: no columnar cache, and this measurement is the evidence that closes the caveat in `130-architecture-facts.md`.** If Export memory for multi-artifact bundles (Candidates + History together) matters enough to fix, the fix is at the streaming/Export implementation level (e.g. do not run sequential full-table passes in one long-lived process without a checkpoint between them), not a store change.
